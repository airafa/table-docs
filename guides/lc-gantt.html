LC Gantt in the table demos ​

New to the implementation? Start with the Table + Gantt 101 walkthrough, which includes complete source blocks, module configuration, and a detailed separator/responsive-width explanation. Run yarn docs:dev at the repository root to read it with VitePress navigation and local search.

The application uses @lc/graphs, not a locally drawn Gantt replacement. Version 0.0.1-rc30 is pinned because it is the registry's current rc release and includes a data-update example. The registry's latest tag still points to the older 0.0.1-rc9.

Documentation sources ​

The published package includes its Storybook documentation and implementation:

  • src/stories/Gantt/Docs.mdx: imports, custom-element registration, composition.
  • src/stories/Gantt/APIs/Gantt.mdx: chart data and date-domain properties.
  • src/stories/Gantt/APIs/GanttRow.mdx: row data and height.
  • src/stories/Gantt/APIs/DataRange.mdx: range styling callbacks.
  • src/stories/Gantt/UpdateData.stories.jsx: replacing chart data.
  • src/webcomponents/Gantt/GanttRow.brick.js: row-data update behavior.

These are installed under node_modules/@lc/graphs. No registry README was available. The local Genie knowledge graph had no matching Gantt entry, so the published source and documentation were used directly.

Each range item has a stable id, type: 'range', and a date pair containing start/end Unix timestamps in milliseconds. The demo adds a name and color. Point items use type: 'point' and one timestamp, rather than a pair. The chart's date_domain is an array of two Date objects. Summary bins count point items; the package does not bin ranges.

Arrays and styling functions are assigned as DOM properties through refs. React 19 can also assign existing custom-element properties directly, but this implementation retains its explicit bridge to coordinate chart and row updates. Assign both the chart's two-dimensional data array and the row's data array when replacing a schedule.

Table integration ​

The title, row controls, and visible-days controls share a single horizontal toolbar. Narrow panels can scroll this toolbar horizontally; the three groups do not become separate lines. Long click-feedback text is visually truncated, but the full text remains in the live status element.

GanttDemo wraps each actual table in a lc-gantt. GanttHeader renders a chart inside the timeline column's th, containing summary bins, the date timeline, and a focus pointer restricted to that 80px header chart. It is not a full-width summary above the table.

The Visible days dropdown selects 7, 14, 30 (default), 60, or 90 days, starting at October 1, 2026 UTC. It updates the actual date_domain of the wrapper, header, and all row charts, rather than applying fisheye distortion. Tick spacing adapts to show approximately six date intervals. Changing the range also centers the focus pointer. Each table maintains its own range.

Moving over the header summary changes only the header focus pointer. The header listens to its own custom focus event and stops the original mousemove event from reaching the outer wrapper, whose pixel width is different. Distortion stays at zero; there is no wheel zoom, zoom slider, or reset button.

GanttCell renders a nested real lc-gantt chart with one canvas-backed lc-gantt-row in each timeline cell. A date-range child draws the task ranges. Its fill/stroke callbacks read each item's color. Each cell has the same selected date domain. The ordinary data columns take only their content width; the timeline takes all remaining table width. Header and cell charts use width: 100% with inline size containment to prevent canvas measurements from forcing the column wider. A 160px minimum keeps the chart usable in narrow panels; the table then scrolls horizontally rather than squeezing the chart to zero width. The header and cells share domain and width; distortion remains zero, so their date-to-pixel scales stay aligned when changing ranges. Pointer movement stays local to the header rather than rerendering every row. The summary and rows scroll horizontally together on narrow screens. Native package resize observers update their canvases as the table divider moves. The column header remains sticky within the table's existing scroll container.

Each row also includes a point/image milestone, adaptive date column dividers, and a click action. Clicking the canvas reports the hit items and UTC date in a live status message. Each cell's accessible description includes the task and milestone dates. The marker uses an existing local SVG rather than fetching an external image.

The summary reserves 48px for the package's double-height canvas (height=24). The timeline explicitly sets width: 100% to avoid its initial zero-width measurement becoming a fixed width in its shadow styles.

Both tables use this same cell renderer and stable record IDs. Sorting moves the timeline with its owning record; it does not require synchronizing a separate chart's row order or scroll position.

The mock generator supplies Plan, Build, and Verify ranges and a completion milestone for every asset. Refresh data replaces the arrays and shifts the ranges without changing task IDs or deliberately remounting visible charts. The revision indicator records the number of replacements.

This is a selectable-date-range rendering demo, not a scheduling editor. Both demos opt into fixed-height row windowing with rowHeight={49}. The table engine still sorts all records, and the summary includes all milestones, but only viewport rows plus four overscan rows on either side mount their charts. Spacer rows preserve the full scroll height. Scrolling unmounts offscreen charts, letting the package clean up their observers and rendering loops. Header and row charts run at 30fps, with at most 20 row charts per demo viewport.

The shared table wrappers preserve their unwindowed behavior when rowHeight is omitted. Windowing requires rows to actually have the supplied fixed height; variable-height rows are not supported. Rows expose their total count and logical row indexes for accessibility, but offscreen content is not in the DOM for browser find or screen-reader browsing until scrolled into view.

The divider coalesces pointer moves into one CSS update per animation frame without rerendering the React panel/module tree for every move. It commits React state on release, cancellation, or lost capture. Keyboard resizing retains the existing bounds and RTL behavior.

Timing ​

The UI reports milliseconds (ms), not nanoseconds. React render to commit is the table component measurement and excludes later custom-element/canvas work. Input to next frame starts before replacing the mock data and ends at a second animation-frame callback after commit, giving the browser a frame opportunity. It includes more of the perceived update but is not a guarantee that every pixel has been presented by the display. Runtime reports retain both measurements; do not compare the React-only value to end-to-end latency.

Validation ​

sh
yarn tables:typecheck
yarn build
TABLE_POC_RUNS=1 yarn tables:runtime --dev both

The browser check exercises both engines, sorting, nonempty canvas drawing, three repeated refreshes with changed pixels and the same connected canvas, all requested element types, summary placement in the column header, summary/timeline/image drawing, actual mouse focus, every visible-days option, exact domain bounds and linear date coordinates, changed canvas pixels without visible-row remounts, matching header and row positions, row click feedback, 1,000-row updates, independent module state, resizing, and mobile horizontal reachability. Resize checks measure the available column space, actual header/row canvas widths, and matching date coordinates at the 25% and 75% panel splits. The checks assert bounded canvas counts and exact row heights, scroll to the last logical record at 1,000 and 5,000 records, refresh while scrolled to the bottom, exercise dragging with both tables at 1,000 records, and require a 1,000-row update within 1.5 seconds and no sampled drag frame stall of 250ms or more. These are regression ceilings, not 60fps guarantees on all hardware.

The production build currently warns that @lc/graphs references D3's unexported utcNice, as well as reporting a large application chunk. The tested demo interactions pass without browser exceptions. This is not validation of every API exposed by the graphs package.

Changing a summary's width dynamically can change D3's generated bin count; this package version does not remove all obsolete bin drawings when that count shrinks. The header observes its width and recreates only the summary on resize or a date-range change, leaving row charts mounted. No dependency internals are patched.
