Minimal table-v9 Engine Package Beside a Design System ​

This guide covers a specific package boundary for a large legacy React/Vite monorepo:

For auditing and closing real legacy timeline compatibility gaps (custom column components, row identity/selection, context menus, row height, Gantt alignment, RTL, and theme), use the Gemma timeline compatibility prompt. It requires source evidence before proposing changes.

text
packages/table-v9/                                  owns TanStack Table v9
packages/design-system/src/component/TableV9/
  TableV9.tsx                                       owns rendered UI and styling

The design system imports the v9 engine facade. The legacy fixed-width v8 table remains where it is and keeps its existing imports. This guide is intentionally independent of any application-specific module loader.

Recommended Ownership ​

  • @company/table-v9: a small engine/API package that pins v9 and exports only the v9 hooks, feature factories, and types the design system needs. It does not render the design-system table.
  • @company/design-system: owns the public TableV9 component, HTML, styles, accessibility behavior, defaults, and documented supported options.
  • Existing v8 package/consumer: unchanged during coexistence.

Do not export v8 and v9 table instances or column types through one shared type surface. Do not call the facade @tanstack/*; use an organization-owned package name to avoid confusing it with upstream packages.

Minimal Steps ​

1. Verify the Baseline and Versions ​

  • [ ] Record package manager, workspace glob, React/React DOM, Vite, current v8 entry point, and lockfile.
  • [ ] Verify the exact v9 version and its React peer requirements from the package registry and matching official docs. latest changes; replace the example version below with the verified and approved version.
  • [ ] Run the existing app build and open the existing fixed-width v8 table before edits.
  • [ ] Check root aliases, resolutions/overrides, Vite optimizer settings, and duplicate React installations.

Gate: the legacy v8 flow is known-good and its package/import boundary is identified.

2. Add the Engine Workspace ​

Create packages/table-v9/package.json and packages/table-v9/src/index.ts. Ensure the root workspace pattern discovers the new direct child packages/table-v9. Do not create a nested table package under packages/design-system for this layout.

Minimal illustrative manifest:

json
{
  "name": "@company/table-v9",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "main": "src/index.ts",
  "types": "src/index.ts",
  "dependencies": {
    "@tanstack/react-table": "9.3.1"
  },
  "peerDependencies": {
    "react": "MATCH_THE_HOST_COMPATIBLE_RANGE",
    "react-dom": "MATCH_THE_HOST_COMPATIBLE_RANGE"
  }
}

9.3.1 is the version exercised in the reference PoC, not a claim about what to install now. Use a range valid for the target app and package policy; do not literally use the placeholder peer ranges. With Yarn Classic, use the repository's existing workspace version convention; with pnpm/Yarn Berry, use the workspace protocol if that's the established convention. Keep React provided by the host rather than bundling a second runtime.

Export a deliberately small v9 surface from src/index.ts. If the design-system wrapper shares a known feature set, let this package own that v9 feature configuration and its corresponding generic column type, for example:

ts
import {
  createSortedRowModel,
  rowSortingFeature,
  sortFns,
  tableFeatures,
} from '@tanstack/react-table';
import type {
  ColumnDef as TanStackColumnDef,
  RowData,
  TableOptions as TanStackTableOptions,
} from '@tanstack/react-table';

export const tableV9Features = tableFeatures({
  rowSortingFeature,
  sortedRowModel: createSortedRowModel(),
  sortFns,
});
export {
  useTable,
} from '@tanstack/react-table';
export type { RowData };
export type ColumnDef<TData extends RowData> = TanStackColumnDef<typeof tableV9Features, TData>;
export type TableOptions<TData extends RowData> = TanStackTableOptions<typeof tableV9Features, TData>;

This is an example for the v9 API used by the reference PoC. Confirm every import and type against the installed v9 version. If a consumer needs a different feature set, make that an explicit package API rather than silently allowing table callers to bypass the design system's supported contract. If v9 changes, this package is the one version-specific boundary to update.

Gate: the package manager installs one v9 copy resolvable from the design-system workspace, while the legacy v8 import still resolves to v8.

3. Make the Design System Depend on the Facade ​

Add @company/table-v9 to packages/design-system/package.json dependencies using that workspace's local-version convention. Keep React/React DOM as design-system peer dependencies as already required by its other React components. Install/update from the monorepo root using the pinned package manager and review the lockfile.

The dependency direction should be:

text
application -> design-system -> table-v9 facade -> @tanstack/react-table v9
application ----------------> legacy v8 package (unchanged)

Do not add @tanstack/react-table v9 to a root override or change the v8 package's dependency to v9. Avoid making the design system depend on an app/module package.

Gate: inspect the installed dependency tree and lockfile; verify v8 and v9 resolve independently and React is not duplicated.

4. Implement TableV9 in the Design System ​

Add packages/design-system/src/component/TableV9/TableV9.tsx (adjust only if the target repository uses a different established folder spelling). Import useTable, tableV9Features, and v9-specific types from @company/table-v9, not directly from TanStack or from a second table major.

Minimum useful public contract:

  • Generic row type and v9-specific columns.
  • Required data and columns.
  • A narrow set of explicitly supported options, loading/empty states, and stable row identity as required by the consumer.
  • Design-system-owned semantic markup, labels, keyboard behavior, overflow, and styles.
  • Only features actually registered in the v9 feature set. For example, if sortable columns are supported, register the sorting feature and sorted row model using the installed v9 API.

Export TableV9 and its public props/type from the design-system's existing component barrel and public package entry point. Do not re-export the entire TanStack package from the design system. Do not make a fake adapter that claims v8 and v9 option/type compatibility.

Gate: a typed consumer can import TableV9 from the design system; no v8 type leaks into its props, and existing v8 consumers compile unchanged.

5. Check Vite and Types in Both Modes ​

  • [ ] Run the focused package/type check and existing production build.
  • [ ] Run the real application in Vite development mode and open both an existing v8 table and a TableV9 consumer at once.
  • [ ] Check browser console/network for missing named exports and inspect resolved workspace module paths if an export is missing.
  • [ ] Check every package main, types, or exports target exists.
  • [ ] Test actual v8 and v9 sorting/data behavior, empty rows, widest columns, horizontal overflow, keyboard use, and simultaneous state.
  • [ ] Clear/restart the Vite dependency optimizer after changing workspace dependencies.

In the reference Vite 5/Yarn setup, the optimizer initially served one TanStack major to both wrappers. The observed workaround was to exclude the table engine packages and prebundle only the v9 adapter that needed CommonJS conversion:

ts
optimizeDeps: {
  exclude: ['@tanstack/react-table', '@tanstack/table-core'],
  include: ['@tanstack/react-store'],
}

Do not copy this config blindly. First reproduce the issue in the target Vite version, inspect the actual failed module, and apply the smallest correction. Dependency topology may differ across Vite and TanStack releases.

Gate: v8 and v9 work together in development and production, with no new browser errors or changes to v8 behavior.

6. Measure Only If the Decision Needs It ​

If bundle cost is a decision criterion, compare identical app builds: existing baseline, existing v8 only, and v8 plus the new v9 consumer. Report emitted compressed asset deltas, shared dependencies, source-map/public-asset treatment, and lazy/eager loading. Do not call the full v9 delta an engine-only cost.

If runtime is a decision criterion, use repeated comparable production runs and realistic data. Label React render-to-commit as including React scheduling and DOM work; do not describe it as isolated TanStack engine speed. Use a real virtualization strategy only if the real consumer needs it.

Minimal File Checklist ​

  • [ ] Root workspace manifest, only if its existing glob does not include packages/table-v9.
  • [ ] packages/table-v9/package.json and packages/table-v9/src/index.ts.
  • [ ] packages/design-system/package.json dependency on the engine workspace.
  • [ ] packages/design-system/src/component/TableV9/TableV9.tsx.
  • [ ] Existing design-system component barrel/public entry export.
  • [ ] One real consumer or integration fixture that renders new v9 beside existing v8.
  • [ ] Focused type/build/dev browser validation and lockfile update.

No application-specific loader, new cross-version abstraction, or mass migration is required unless the target project explicitly needs it.

Stop Conditions ​

Stop and resolve the issue before adopting v9 if the host React peer range is unsupported, the workspace manager forces both TanStack majors to one copy, Vite serves the wrong major in development, the v9 package entry/type exports do not resolve, or the existing v8 flow changes unexpectedly.
