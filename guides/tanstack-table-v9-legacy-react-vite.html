Adding TanStack Table v9 Beside a Legacy v8 Table ​

An interactive, staged playbook for introducing a flexible v9 table to a large React/Vite monorepo while the existing fixed-width v8 table remains supported.

For a chronological record of the approaches attempted, observed failures, fixes, and measurement caveats from the reference implementation, see the PoC session retrospective.

For the narrower package split where packages/table-v9 owns the engine and the design system owns TableV9.tsx, see the minimal engine-package guide.

Working rule: keep v8 working, add v9 beside it, and move one explicitly selected use case at a time. Do not turn an adoption PoC into a cross-version abstraction or a repository-wide migration.

How to Use This Playbook ​

Work through the stages in order. Check items only after verifying them in the target repository. Each stage ends in a gate: stop there, review the evidence, and decide whether to continue. If a gate fails, fix or document it before moving on.

  • [ ] Record the application, package manager, React version, Vite version, current TanStack versions, and intended v9 version.
  • [ ] Choose one representative table/module with realistic data and production loading behavior.
  • [ ] Decide whether this is only a side-by-side PoC or an approved migration of a named consumer.
  • [ ] Keep a short decision log: date, evidence, unresolved risks, and stage approval.

No-go conditions: the v8 package cannot be independently pinned; the real application does not run in the proposed baseline; or the requested v9 release/React compatibility cannot be verified. Resolve these before implementation.

Target Shape ​

text
legacy React app / module loader
  module-report-v8  ---> design-system/table-v8 ---> TanStack Table v8
  module-report-v9  ---> design-system/table    ---> TanStack Table v9

Keep the application module and design-system wrapper as separate ownership boundaries. Each wrapper owns its TanStack imports and version-specific types. Share only engine-neutral components, data contracts, styles, or demo controls. Do not pass table instances, feature objects, or ColumnDef types across the v8/v9 boundary.

The v9 table is headless: the design system still owns markup, accessibility, visual styles, defaults, and supported extension points. Expose the native v9 capability required by consumers without promising that every v8 option or behavior maps identically.

Stage 0: Discover and Baseline ​

Actions ​

  • [ ] Find the existing v8 wrapper, its direct consumers, package manifests, lockfile, module loader, lazy-loading path, layout configuration, and CI/build commands.
  • [ ] Record whether v8 is bundled once, repeated across chunks, dynamically loaded, or relied upon by non-React consumers.
  • [ ] Verify the exact installed v8 package and current v9 release through the package registry and official migration/React docs. Record the checked date. Treat “latest” as moving, not as a version string.
  • [ ] Verify peer dependencies against the app's actual React and React DOM versions.
  • [ ] Build and launch the complete app before editing. Save baseline build output and at least one runtime sample on representative hardware.
  • [ ] Identify user-visible contracts: fixed column widths, overflow, sorting/filter semantics, pagination ownership, selection, keyboard behavior, row identity, and persisted state.

Gate ​

Can the unchanged app build and can the representative legacy v8 table be demonstrated? If not, first capture and resolve the baseline failure; do not attribute it to the v9 integration.

Decision: baseline accepted / baseline blocked: ____________________

Stage 1: Choose the Coexistence Boundary ​

Recommended default ​

Add explicit sibling workspaces, for example:

text
packages/design-system/table-v8     -> @company/table-v8 -> @tanstack/react-table v8
packages/design-system/table        -> @company/table    -> @tanstack/react-table v9
modules/report-table-v8
modules/report-table-v9

Use names that match local conventions. The important part is explicit package ownership, not these literal names.

Actions ​

  • [ ] Pin each TanStack major in the package that imports it; use the repo's lockfile and package manager.
  • [ ] Keep React and React DOM as host/peer dependencies where consistent with the monorepo's package policy. Avoid shipping a second React runtime.
  • [ ] Keep the existing v8 package entry point and export surface stable.
  • [ ] Give v9 its own package entry point and v9-specific types.
  • [ ] Decide whether consumers need the raw engine, a styled component, or both. Prefer the smallest supported public API.
  • [ ] Keep only truly version-neutral code shared between wrappers.
  • [ ] Inspect root resolutions, aliases, overrides, hoisting rules, and lockfile behavior. Never force both TanStack majors to one resolved version.

Gate ​

Can the package manager resolve both majors from their respective workspace consumers, with one React runtime and unchanged v8 imports? Check the installed dependency tree and lockfile, not just package.json declarations.

Decision: package boundary accepted / revise: ____________________

Stage 2: Make Vite Resolve Each Major Correctly ​

Vite's development dependency optimizer can prebundle a package by bare import name. In a monorepo, both wrappers import @tanstack/react-table; an overly broad optimizer or alias can make a v8 consumer receive v9 exports, or vice versa. A production build alone does not detect this development-only failure.

Actions ​

  • [ ] Inspect the actual dependency IDs, Vite config, workspace symlinks, optimizeDeps, aliases, and dedupe settings.
  • [ ] If the optimizer merges the majors, exclude the version-sensitive table engines from prebundling and include only adapters that need CommonJS conversion.
  • [ ] In the validated reference app, Vite 5 required:
ts
optimizeDeps: {
  exclude: ['@tanstack/react-table', '@tanstack/table-core'],
  include: ['@tanstack/react-store'],
}
  • [ ] Treat that snippet as a diagnosis-backed example, not a universal Vite recipe. Check the actual installed Vite and TanStack adapter versions; v9 dependency topology can change.
  • [ ] Restart Vite and clear/rebuild its optimizer cache after changing dependency or optimizer configuration.
  • [ ] Load the real app in development and verify both tables render without missing-export errors.

Gate ​

Can a real v8 consumer and a real v9 consumer load simultaneously in development and production? Confirm each version's expected exports and inspect browser console/network errors.

Decision: dev and production coexistence accepted / blocked: ____________________

Stage 3: Implement the Smallest Useful v9 Wrapper ​

Actions ​

  • [ ] Build a generic v9 component in the v9-owned package using only v9 imports and types.
  • [ ] Start with a small documented feature set. For example: core rows, sorting, stable row IDs, custom header/cell rendering, and controlled options actually needed by the selected consumer.
  • [ ] Register v9 features and row-model factories explicitly where the installed v9 API requires them. Do not copy v8 setup calls into v9 based on name similarity.
  • [ ] Keep ColumnDef exported from the v9 wrapper's own package. Keep the v8 ColumnDef imported from its v8 wrapper.
  • [ ] Define the wrapper's defaults and contracts: width policy, overflow, empty/loading/error states, labels, keyboard interaction, and row identity.
  • [ ] Expose a narrow options or explicit props surface. Do not leak arbitrary library options without deciding whether the design system supports their behavior.
  • [ ] Keep virtualization out of the first comparison unless real data volume requires it. If it does, use and measure a suitable established virtualizer rather than rendering thousands of DOM rows and calling it a library benchmark.

Gate ​

Does the v9 package work with typed mock data and the selected feature set, while its public API contains no v8 types or imports? Do v8-only consumers remain unchanged?

Decision: v9 wrapper accepted / revise: ____________________

Stage 4: Register a Real App Module ​

Actions ​

  • [ ] Add a separate application module for the v9 table using the repo's existing module lifecycle and React mount/unmount pattern.
  • [ ] Add it to the module loader/registry and layout configuration using existing app conventions.
  • [ ] Render the v8 and v9 modules on the same real page with visibly distinct version labels and equivalent mock data.
  • [ ] Give the two demos independent state. Changing one row count or sort order must not alter the other.
  • [ ] Exercise the standard module editor, layout, localization, directionality, and responsive behavior where applicable.
  • [ ] Stop demo events from bubbling into host editor selection only if that is the host's expected interaction contract; avoid blanket propagation suppression for unrelated controls.
  • [ ] If the design calls for adjacent resizable tables, test divider pointer, keyboard, RTL, clamp, and mobile behavior separately from table engine behavior.

Gate ​

Do both tables render and function inside the same application module/layout path? Does the rest of the application, including its legacy tables, still work?

Decision: real-app integration accepted / blocked: ____________________

Stage 5: Validate Types and Behavior ​

Minimum checks ​

  • [ ] Run the normal production build.
  • [ ] Run a focused TypeScript check for both table packages and their consuming modules.
  • [ ] Run existing relevant tests; add the smallest project-native regression test for behavior that could otherwise silently break.
  • [ ] Verify v8 and v9 package imports resolve from their real module locations, not only from a hand-written root-level example.
  • [ ] Check package types/exports metadata against files that actually exist. A broken types path can be hidden by Vite while failing editor and CI resolution.
  • [ ] Check browser errors in both Vite development mode and the production preview.
  • [ ] Verify sorting, stable row identity, data refresh, empty data, widest header/cell, horizontal overflow, keyboard use, and simultaneous module mounting.
  • [ ] Verify independent state and, if included, splitter bounds and responsive layout.

Gate ​

Can another developer reproduce all checks using documented commands? No new errors, generated source files, or unrelated formatting churn should be hidden in the result.

Decision: validation accepted / remaining failures: ____________________

Stage 6: Compare Bundle and Runtime Cost ​

Comparable build stages ​

Build the same app, configuration, toolchain, and public assets for these stages:

StageIncluded table modulesQuestion
baselineNeither PoC moduleWhat is the app cost before the feature?
v8Existing or reference v8 module onlyWhat does the old implementation add?
bothv8 and v9 modulesWhat is the incremental cost of coexistence?

If the normal application already contains v8, do not pretend that baseline is a real user build without it. Report both the real production baseline and the staged isolation comparison.

Actions ​

  • [ ] Use bundler metadata to report raw and compressed emitted assets, per-chunk sizes, and module attribution.
  • [ ] Exclude source maps from user download totals; state whether copied public assets are included.
  • [ ] Report entry/static dependency closures carefully. Shared dependencies occur in multiple closures, so do not sum closures as incremental cost.
  • [ ] Report the delta from v8-only to v8+v9, not only a repository-wide total.
  • [ ] Measure cold and warm application startup separately if startup is a concern; identify whether module chunks are eagerly or lazily loaded.
  • [ ] In a browser, measure table render/update-to-commit and app-level navigation/readiness. Use the same browser, machine, data, production mode, and repeated runs; report medians and samples.
  • [ ] State what each timer includes. React commit time includes React scheduling and DOM work; it is not an isolated table-engine benchmark and is not the same as final paint.
  • [ ] If the app depends on maps, APIs, or external tiles, make readiness assertions independent of those external services unless they are specifically under test.
  • [ ] Use realistic enterprise data shape, feature mix, row count, and likely virtualization strategy. Keep benchmark pages in the real app.

Gate ​

Do the measurements answer an explicit decision, and can they be repeated? If not, report them as exploratory observations, not a go/no-go benchmark.

Decision: performance evidence accepted / collect more evidence: ____________________

Stage 7: Roll Out Incrementally ​

Actions ​

  • [ ] Identify a named, low-risk consumer that needs v9 flexibility; preserve v8 as the default for unconverted consumers.
  • [ ] Move only that consumer to the v9 wrapper. Do not migrate by package-wide find-and-replace.
  • [ ] Compare user-visible behavior and data results, not just screenshots or TypeScript compilation.
  • [ ] Add a rollback path: return that consumer to its v8 import/module without changing other consumers.
  • [ ] Record owner, target consumers, support window, and exit criteria for v8.
  • [ ] Remove v8 only after inventory shows no remaining consumers, supported products approve the removal, and a separate deprecation/removal change passes compatibility checks.

Gate ​

Has the named consumer passed functional and performance checks, and is rollback straightforward? If not, keep v9 opt-in and do not retire v8.

Decision: rollout accepted / continue PoC / roll back: ____________________

tsc unexpectedly creates .js beside TypeScript filesCLI flags/scripts were not applied as expectedInspect the exact command and outputs; use the repo's pinned tsc binary and a checked-in narrow script; remove only known generated files

Reference-Project Notes ​

The reference implementation used Yarn Classic workspaces, React 18, Vite 5, TanStack Table v8.21.3 and v9.3.1, and dynamically loaded application modules. The v9 version was the registry's latest at implementation time; always recheck before starting a new adoption.
