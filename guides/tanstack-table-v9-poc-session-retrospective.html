TanStack Table v9 PoC: Session Retrospective ​

This document records what was tried while adding TanStack Table v9 beside v8 in this React/Vite module-based application, including mistakes, observed failures, fixes, and limits of the evidence. It is a practical supplement to the staged adoption playbook, not a claim that every other monorepo will behave the same way.

What Was Built ​

  • Two nested design-system workspaces: @starterkit/table-v8 using TanStack Table 8.21.3 and @starterkit/table using 9.3.1, which was reported as npm latest at implementation time.
  • Two separate Baseplate modules, loaded by the real app module loader and rendered on the same application page.
  • Independent mock-data controls, sorting, render-to-commit samples, and a draggable table divider with 25–75% bounds.
  • Baseline, v8-only, and dual-version production bundle/runtime measurement stages, plus a Vite development-mode regression check.
  • A staged adoption playbook and a system prompt for a local Gemma model.

The versions above are historical observations, not recommendations for a new adoption. Verify the registry, official docs, peer requirements, and local lockfile at the time of use.

Validate table features only by seeing headers/dataThis missed regressions in independent module state, sorting, refreshing, large row updates, responsive sizing, and the new divider.Add browser automation against production preview and Vite dev for both modules, checking row counts, sorting, refresh, state isolation, errors, mobile layout, divider bounds, complementary widths, and keyboard commands.Test the user's actual integration workflows, not merely component presence.

Measurement Snapshot and Limits ​

The checked-in reports represent one machine/browser/toolchain run from the PoC, not a general performance guarantee. The measured bundle delta between v8-only and both-version stages included the v9 module and its integration surface, demo controls, styles, and bundler chunking effects; it was not an engine-only measurement. Runtime values vary across runs and development timings are not comparable to production timings.

For a new decision, regenerate the reports with the same machine, browser, production mode, data, and stage configuration. Prefer repeated median samples. Use the reference results to validate that the scripts work, not as an acceptance threshold for a larger application.

Practical Checklist for Reuse ​

  • [ ] Begin with the real app and preserve its working v8 baseline.
  • [ ] Pin each major in its own workspace and verify the dependency tree.
  • [ ] Inspect Vite dev resolution independently of production build output.
  • [ ] Check package entry points and TypeScript ambient declarations.
  • [ ] Add real app modules before drawing integration conclusions.
  • [ ] Exercise both modules concurrently and test host event behavior.
  • [ ] Define what each bundle and runtime metric includes.
  • [ ] Keep results reproducible, rollback easy, and v8 consumers unmigrated until explicitly approved.
