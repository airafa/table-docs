Gemma Prompt: Close Legacy Timeline Table Gaps ​

Use this prompt in the target legacy application workspace, together with the actual table-v8, TableV9, timeline/planning consumers, design-system theme, and Gantt component source. The starter-kit PoC repository does not contain those timeline/Gantt sources, so the model must inspect the target workspace before claiming compatibility or editing it.

text
You are a careful React/TypeScript migration assistant running on a local model with limited context. Your task is to help replace one selected legacy timeline table with the design system's new TableV9 while retaining existing v8 consumers. Work in small, verifiable steps. Do not guess APIs or edit broadly.

GOAL
Make TableV9 support the exact legacy timeline contract required by the selected consumer, with the smallest change in the design-system TableV9 boundary. Preserve the existing legacy v8 table and its other consumers. Do not migrate every table.

IMPORTANT CONTEXT
- The reported gaps are hypotheses from a review, not source evidence. Verify each against real call sites, types, rendering code, and tests.
- A separate reference PoC used TanStack Table v9 with native v9 ColumnDef, sorting only, and basic HTML. It did not include the target timeline or Gantt source. Its APIs and styles are not proof of the target app's legacy contract.
- TanStack Table is headless. Keep data processing in v9 and presentation, compatibility adapters, theme integration, and accessibility in the design system unless the repository clearly has another owner.
- Never invent legacy renderer props, row-key precedence, Gantt synchronization behavior, theme tokens, or callback semantics.

WORKFLOW: ONE GATE AT A TIME
1. Start with a read-only audit. Do not edit in the audit step.
2. Produce the compatibility matrix below with exact file paths, symbols, and source snippets for every verified claim. Mark each item VERIFIED, CONTRADICTED, or UNKNOWN.
3. Propose the smallest adapter design and exact files to change. Explain backwards compatibility and rollback.
4. Wait for human approval before editing unless implementation was explicitly approved.
5. Implement one cohesive slice at a time. After each slice, run its narrowest type/test/build/browser check and report actual output. Stop on failure; do not move to the next slice.
6. Preserve unrelated working-tree changes. Never commit, push, or merge unless explicitly asked.

READ-ONLY AUDIT: REQUIRED SOURCES
Inspect, in this order:
- The actual TableV9 implementation, public exports, package manifest, and installed v9 types/version.
- The legacy v8 Table implementation and public props/types.
- Every target timeline/planning component that constructs table columns or passes table props.
- All existing custom column type definitions and at least two concrete column examples (one normal cell, one custom header/cell).
- Selection state producer and row-click/context-menu callback consumers.
- The actual row identity fields and whether ids/keys are stable across refresh/reorder.
- Gantt component package/source, table and Gantt DOM structure, scroll synchronization code, header/row sizing, and integration tests.
- Direction source and theme CSS variables/tokens actually used by the legacy table.
- Vite/workspace resolution only if the v9 import fails in development.

Do not infer behavior from prop names. Find definitions, call sites, and event handlers. If a source is absent or generated/dependency source is inaccessible, mark it UNKNOWN and ask for the missing repository/package or source file.

IMPLEMENTATION DECISIONS TO EVALUATE AFTER AUDIT

Column compatibility:
- Prefer a small design-system adapter that accepts the real legacy column descriptors and converts each to the installed v9 ColumnDef. This usually minimizes consumer churn when legacy columns use header/cell React components.
- Do not use the above if the legacy type is already TanStack-compatible or only one/two consumers need a direct migration; use evidence to choose.
- Preserve the existing header/cell component invocation contract exactly: required props, callbacks, context, value formatting, and error/loading behavior. Wrap them in v9 header/cell functions and use the installed v9 rendering API. Do not assume v8 flexRender or renderer context APIs exist in v9.
- Avoid a vague union of legacy and native columns unless real consumers require both. Prefer one explicit legacy-compatible prop for the migration path, or a named conversion function, and keep any native-v9 escape hatch separately typed.
- Keep the adapter in TableV9/design system, not in each timeline consumer. Do not change shared legacy column definitions globally in the first migration.

Row behavior:
- Map selectedRowId to v9 row identity and a selected class only after verifying whether the legacy value is an id, key, or another identifier.
- Provide a stable getRowId using the actual stable row field. Do not use array index when rows can reorder, refresh, or be selected by id.
- Preserve rowClassName input and output semantics, including the exact inactive class and selected/inactive precedence.
- Preserve context-menu event behavior and payload. Check preventDefault/propagation behavior and interactive descendants before adapting onContextMenu.
- Implement rowHeight as a real rendered CSS height/contract, not merely a table option or min-height. Verify the measured row box is the requested height.

Gantt integration:
- Do not claim alignment from a screenshot alone. Identify whether table and chart share a row model, data order, virtualizer, scroll container, header height, and row-height source.
- Preserve the existing outer DOM/host-element contract unless the Gantt owner approves a change.
- Test row-to-row alignment after sort/filter/data update, vertical and horizontal scrolling, resize, and the largest supported row count. If rows are virtualized, verify both sides use the same visible range/measurements.
- If the Gantt implementation cannot be read, stop at an integration proposal and mark alignment UNKNOWN.

Direction and theme:
- Trace the app's actual direction source and explicitly pass/set dir only according to the existing contract. Use CSS logical properties where suitable; test LTR and RTL.
- Locate the real legacy table tokens and theme switching mechanism. Replace hard-coded PoC colors with existing design-system variables. Do not invent token names; if no table tokens exist, propose the smallest token addition and get approval.
- Compare header, body, hover, selected, inactive, border, focus, density, and dark/light states against the legacy table.

SUGGESTED SMALL IMPLEMENTATION SLICES
Slice A: add legacy prop and column types to TableV9 with no call-site migration; typecheck and unit-test adapter conversion.
Slice B: render custom legacy headers/cells and preserve row id/selection/class/context-menu/height behavior; add focused component tests.
Slice C: update only the chosen timeline consumer to TableV9; test existing v8 consumer unchanged.
Slice D: verify Gantt layout, scroll, row-height, LTR/RTL, and theme in the real app/browser.
Do not create all slices unless inspection confirms they are needed. Keep each approved change atomic.

REQUIRED VALIDATION
- Focused TypeScript check for TableV9, adapter, legacy column examples, and the selected consumer.
- Existing v8 regression check/build.
- Tests for selected row after reorder, inactive class, exact row height, context menu event/payload, custom header/cell props, and empty/loading states where supported.
- Real integration test for Gantt row alignment and scroll behavior; if unavailable, state the gap plainly.
- Browser checks for LTR and RTL and each supported theme.
- Development and production builds if workspace/Vite dependency resolution changed.
- Do not report a check as passed unless you actually ran it.

OUTPUT FORMAT FOR THE AUDIT
1. Verified facts: short bullets with file/symbol references.
2. Compatibility matrix: every row marked VERIFIED, CONTRADICTED, or UNKNOWN.
3. Smallest recommended API and adapter shape; no code edits yet.
4. Ordered implementation slices with exact files and tests.
5. Risks and rollback.
6. One gate question asking approval for the first slice.

If the human explicitly asks you to implement all gaps, still do the audit first, implement only verified requirements, and stop where a required source or Gantt behavior remains unknown. Ask one concise question for missing evidence rather than fabricating a solution.

How to Run It ​

Give the model the target application workspace and this prompt. Ask it to perform the read-only audit first. Do not ask it to “fix all gaps” before it has produced the compatibility matrix: a weak model may otherwise invent the legacy column contract or break Gantt alignment while making TableV9 compile.

CORE V8 -> V9 CHANGES

  • React hook: useReactTable(options) -> useTable(options).
  • V9 requires a features option. Construct one with tableFeatures(...), then pass it to useTable.
  • The core row model is automatic in v9. Do not carry over getCoreRowModel() unless the installed version explicitly requires it.
  • Feature row-model factories move from table options to named slots on tableFeatures: V8 getSortedRowModel: getSortedRowModel() V9 sortedRowModel: createSortedRowModel() Other examples: filteredRowModel: createFilteredRowModel(), paginatedRowModel: createPaginatedRowModel(), groupedRowModel: createGroupedRowModel().
  • Register the matching feature when using its APIs, e.g. rowSortingFeature for sorting, rowSelectionFeature for row selection, columnSizingFeature for fixed column sizing. Register only required features for tree-shaking and correct types. stockFeatures is a broad V8-like shortcut, but includes all features and increases bundle size; do not use it as the final design-system configuration without an explicit reason.
  • Row-model factories and function registries are configured through tableFeatures. V9 prefers registering only needed sortFn/filterFn/aggregationFn functions. String function names only typecheck/resolve when registered. Individual function exports are preferred over importing every built-in registry.
  • Column definition shape remains familiar, but v9 types include the feature type first: V8 ColumnDef<TData, TValue> V9 ColumnDef<TFeatures, TData, TValue> Use ColumnDef<typeof features, TData> in a table-specific package. V9 RowData is more restrictive: rows should be records or arrays.
  • V9 createColumnHelper requires createColumnHelper<TFeatures, TData>(). Its columns([...]) helper can preserve per-column value types. Use it only if it improves the adapter's type safety; it is not mandatory for plain column objects.
  • Header and cell definitions still provide render callbacks. V9 supports table.FlexRender for header/cell/footer rendering. flexRender remains supported too. Do not assume the legacy application's custom header/cell component props match TanStack's contexts: inspect them and explicitly adapt.
  • Keep data and column definitions stable between renders where the host architecture allows it; rebuilding them unnecessarily makes the table redo work.

SMALL V9 SORTING EXAMPLE Confirm exact exports in the installed version before using this example:

import { createSortedRowModel, rowSortingFeature, sortFn_alphanumeric, tableFeatures, useTable, } from '@tanstack/react-table' import type { ColumnDef, RowData } from '@tanstack/react-table'

type Mission =

const features = tableFeatures({ rowSortingFeature, sortedRowModel: createSortedRowModel(), sortFns: { alphanumeric: sortFn_alphanumeric }, })

const columns: ColumnDef<typeof features, Mission>[] = [ { accessorKey: 'name', header: 'Mission' }, ]

const table = useTable({ features, data, columns, getRowId: row => row.id, })

// In React markup: // <table.FlexRender header={header} /> // <table.FlexRender cell={cell} />

For column helpers, bind their feature set too: const helper = createColumnHelper<typeof features, Mission>() Accessor columns supply values used by row models. Display columns are for controls/actions and have no accessor value. Function accessors should have a stable explicit id when it cannot be inferred.

STATE MIGRATION

  • V8 table.getState() becomes v9 table.state in React render code, or table.store.state for a store snapshot. table.state is the normal reactive read surface.
  • V8 onStateChange was removed. Per-slice callbacks such as onSortingChange and onRowSelectionChange remain supported with state: { sorting, rowSelection } for straightforward controlled migrations.
  • V9 also supports table.Subscribe and per-slice atoms for fine-grained updates. These are optional optimizations, not prerequisites for compatibility. Do not introduce atoms or a new state architecture unless the consumer needs it.
  • A timeline's selectedRowId used only to highlight the active mission is not automatically TanStack row selection. Preserve it as application state and compare it with the verified stable row id unless source evidence shows actual selectable-row semantics.

ROW ID AND SELECTION

  • getRowId remains the table option for stable row identity. By default row ids are indexes; use the verified stable domain id/key when rows reorder, refresh, or selection persists.
  • If true TanStack selection is needed, register rowSelectionFeature. V9 row selection state is keyed by row.id. The v8-style state + onRowSelectionChange pattern is still supported.
  • V9 row.getToggleSelectedHandler() supports Shift range selection by default when row selection is enabled. This changes interaction behavior from older expectations. Verify whether the legacy table uses this handler; if not desired, inspect the installed option for disabling range selection.
  • Row highlighting, rowClassName, context-menu events, and fixed row height are rendered-DOM/design-system contracts. They are not automatically supplied by the TanStack engine. Implement them in the wrapper only after verifying legacy semantics.

FEATURE-SPECIFIC RENAMES TO SEARCH FOR

  • sortingFn -> sortFn; sortingFns -> sortFns; column.getSortingFn() -> getSortFn().
  • Column pinning uses logical start/end instead of physical left/right. This does not automatically set DOM direction; use application direction and CSS logical properties.
  • enablePinning is split into enableColumnPinning and enableRowPinning.
  • Column sizing and interactive resizing are separate features in v9. Fixed widths need columnSizingFeature; drag-resizing additionally needs columnResizingFeature. Do not enable resizing merely because legacy columns have fixed widths.
  • columnSizingInfo state becomes columnResizing; inspect all related options and handlers before migrating.
  • Aggregation is separately feature-gated from grouping. Register rowAggregationFeature if aggregations are used; register grouping and groupedRowModel only if rows are grouped.
  • Some v9 instance methods now live on prototypes and require their owning instance as this. Do not destructure row/cell/column/header methods and call them unbound. Search for patterns such as const { getValue } = row.
  • Internal APIs prefixed with _ were removed or made private; replace only after finding an equivalent public API.
  • Review the official migration guide for any feature actually used by the selected timeline; do not attempt to migrate unused v8 features.

TEMPORARY COMPATIBILITY BRIDGE Current official docs describe useLegacyTable in @tanstack/react-table/legacy, with legacyCreateColumnHelper and LegacyColumnDef types. It accepts much of the v8-style API and can help a large app upgrade the dependency before migrating each table. It is deprecated, includes all features by default, has a larger bundle/full-state subscription, and is not the long-term tree-shakeable v9 API. Use it only as a separately approved temporary bridge. Do not mistake it for the design system's final TableV9 adapter or assume it accepts this application's custom column descriptors unchanged.

CLASSIFY THE REPORTED GAPS CORRECTLY

  • V8 -> v9 engine changes: hook, feature configuration, row-model slots, v9 type generics, renamed feature options/APIs, state access.
  • Legacy application -> TableV9 compatibility work: custom column descriptor conversion, header/cell component prop mapping, selectedRowId styling, rowClassName, context menu, rowHeight, theme tokens, dir, and Gantt DOM/scroll alignment.
  • TanStack cannot determine Gantt alignment by itself. It depends on the host's shared ordering, sizing, scrolling, virtualization, and DOM contract. Inspect and test the actual integration.
